# 스파이크: OPA/Rego 교체 검토 (vs 현 YAML 정책 엔진)

> 유형: 의사결정 메모 (구현 아님). S5 stretch P5 3순위.
> 질문 (design.md:101): YAML 자체 엔진으로 충분한가? OPA가 면접 시그널 가치가 있는가?
> 결론: **이 프로젝트에서는 YAML 유지. OPA는 "실서비스 전환 시 마이그레이션 경로"로 문서화.**
> 관련: gateway/src/gateway/policy.py, docs/specs/04-auth-policy-audit.md, docs/design/agentops-gateway-design.md

---

## 1. 현 YAML 엔진이 실제로 하는 일

`policy.py` ~120줄로 다음을 모두 충족한다:

- **default-deny 화이트리스트** — 명시 허용 조합만 통과, 나머지 전부 거부
- **데이터/코드 분리** — 매트릭스는 `policy.yaml`, 판정 로직은 `policy.py`. 권한 변경은 YAML 한 줄
- **fail-closed** — `evaluate`는 어떤 기형 입력에도 예외 없이 항상 `Decision` 반환
- **인자 레벨 제약** — `query_logs`의 `max_range_hours: 24` (현재 유일)
- **오타 가시화** — `warn_unknown_tools`가 기동 시 미존재 tool 이름을 로그로 노출
- **출력 계약** — `Decision.rule` = `"agent:server:tool"` + `POLICY_DENIED` payload를 S6 데모·audit 페이지가 파싱

현재 정책 규모: **3 에이전트 × 3 서버, 인자 제약 1종.**

---

## 2. OPA/Rego가 가져오는 것

| 능력 | YAML 엔진 | OPA/Rego |
|------|-----------|----------|
| 정책 표현력 | 화이트리스트 + 제약 1종(시간 범위) | 임의 로직 — 조건·집합·재귀·외부 데이터 조인 |
| 정책 배포 | 기동 시 1회 로드, 핫 리로드 없음 | bundle 배포 + 핫 리로드 |
| 의사결정 위치 | 인프로세스 함수 호출 | 사이드카(HTTP) 또는 인프로세스(wasm/Go lib) |
| 테스트 | pytest 단위 테스트 | `opa test` 내장 프레임워크 |
| 표준성 | 자체 구현 | CNCF graduated, 업계 표준(authz의 사실상 기본값) |
| 결정 로깅 | 자체 audit JSONL | OPA decision log 내장 |

## 3. 교체 비용

- **신규 의존성·운영 표면**: 사이드카 방식이면 별도 프로세스 + 네트워크 홉(latency). 인프로세스(wasm/cffi) 방식이면 빌드 복잡도 + 바이너리 의존.
- **Rego 학습 곡선**: Rego는 선언적이고 진입장벽이 높다. 3×3 매트릭스를 표현하는 데 드는 인지 비용이 현 YAML보다 **높다**.
- **계약 보존 부담**: 현 `POLICY_DENIED` payload(`rule`, `agent`, `detail`)는 S6 데모·audit 페이지의 **고정 인터페이스**다. Rego 출력을 이 형식으로 정확히 매핑하는 어댑터를 새로 만들고 테스트해야 한다 — 순수 추가 작업이지 가치 추가가 아니다.
- **과잉 설계**: OPA의 표현력(외부 데이터 조인, 복잡 조건)은 현 정책이 전혀 요구하지 않는다. 3×3 + 시간 제약 1종에 OPA는 명백한 오버킬이다.

---

## 4. 면접 시그널 분석 (design.md:101 핵심 질문)

이 프로젝트는 데모/포트폴리오다 (design.md 전제 1). 면접 시그널 관점:

- **OPA를 붙이는 것**: "OPA 써봤다"는 이력서 키워드는 얻지만, 3×3 매트릭스에 사이드카를 다는 것은 **판단력 부족 신호**로도 읽힌다 — 도구를 문제 크기에 맞추지 못함.
- **OPA를 검토하고 안 쓰는 것 (이 메모)**: "평가했고, 현 규모엔 자체 엔진이 더 단순·안전해서 채택하지 않았으며, 실서비스 멀티테넌시·동적 정책 단계에서 OPA로 전환한다"는 **명시적 판단**이야말로 더 강한 시그널이다. 도구를 아는 것 < 언제 쓸지 아는 것.
- 즉 **이 메모 자체가 산출물이자 시그널**이다. 구현이 아니라 의사결정의 가시화.

## 5. 결론과 전환 트리거

**결정: YAML 엔진 유지.** 현 규모에서 OPA는 비용 > 편익.

OPA 전환을 정당화하는 **구체 트리거** (이 중 하나라도 발생 시 재검토):

1. **정책 핫 리로드 요구** — 재기동 없이 정책 변경이 운영 요건이 됨
2. **표현력 한계 도달** — `max_range_hours` 같은 ad-hoc 제약이 3종 이상 쌓여 `_check_args`가 분기 지옥이 됨
3. **멀티테넌시** — 테넌트별 정책 분리·외부 데이터(조직도, 등급) 조인이 필요해짐
4. **정책 작성자 ≠ 코드 소유자** — 보안팀이 엔지니어 배포 없이 정책을 직접 관리해야 함

트리거 전까지 YAML이 정답이다 — 더 단순하고, 감사 가능하고(120줄), fail-closed가 코드로 자명하다.
