## Problem Statement

레포는 S1–S6 + stretch까지 완성돼 97 테스트 그린 상태(2026-06-20 마지막 커밋)이고, 설계·아키텍처·학습 문서까지 갖췄다. 하지만 **채용담당자 관점에서 이 레포가 증명하는 것은 "설계하고 구현했다"까지다.** `docker compose up` 한 줄로 도는 6서비스는 배포·운영 경험의 증거가 아니다.

동시에 07-06에 승인된 Evidence Box 파일럿은 8주간 0줄 구현 상태이며, 그 진행은 상대 회사 담당자와의 2차 대화 일정에 묶여 있다. 즉 **혼자 끝낼 수 있는 트랙이 지금 없다.**

이 문서는 그 공백을 메운다: 기존 자산을 K8s에 올려 "배포·운영까지 했다"로 확장하되, 흔한 매니페스트 작성이 아니라 **이 코드베이스에만 존재하는 문제**를 캐낸다.

## Demand Evidence

**현재 0. 07-06 문서와 같은 방식으로 정직하게 기록한다.**

사용자는 "지금 잡서치 타이밍", "LLMOps 성향 JD에서 요구하는 조합 그대로"라고 진술했지만, **이 세션에서 실제 JD는 한 건도 제시되지 않았다.** 즉 "K8s + vLLM 조합이 타깃 JD의 요구사항과 일치한다"는 주장은 현재 미검증 가설이다.

카테고리 수준 증거는 있다:
- 플랫폼/인프라 엔지니어 채용에서 K8s는 사실상 기본 요구사항 (일반 상식 수준)
- 관측성 스택(OTel/Prometheus/Grafana)은 이미 레포에 구현돼 있어 K8s 승격 비용이 낮음

하지만 이건 "이 사람의 타깃 포지션"에 대한 증거가 아니라 "직군 전반"에 대한 증거다. 06-10 문서에서 "MCP gateway 카테고리 증거 ≠ 이 제품 수요 증거"라고 구분했던 것과 정확히 같은 구분이다. → **The Assignment로 이월.**

## Status Quo

**레포 현황 (2026-08-14 실측):**
- 마지막 커밋 2026-06-20. 8주 무커밋. 워킹트리 클린, 브랜치 `main` 단독.
- 6서비스 compose: gateway(:8000) + ticket/docs/ops(:8101–8103) + prometheus(:9090) + grafana(:3000)
- 97 테스트 그린, CI에 lint + pytest + compose e2e 잡 존재
- Prometheus는 `static_configs: ["gateway:8000"]` 단일 타깃
- **OTel trace는 `ConsoleSpanExporter`로 stdout에만 출력 — OTLP 배선 없음.** 계측은 있으나 파이프라인은 없다.

**게이트웨이의 상태 보유 지점 (K8s 도입의 핵심 — 코드 실측):**

| 상태 | 위치 | `replicas: 3`에서 벌어지는 일 |
|---|---|---|
| MCP 세션 | `app.py` `StreamableHTTPSessionManager(app=server)` — `stateless=True` 미지정 | `mcp-session-id`가 다른 파드로 라우팅되면 세션 미존재. 핸드셰이크 파손 |
| audit 로그 | `audit.py` → 로컬 `audit.jsonl` 파일 | 파드마다 별도 파일. `/admin`은 자기 파드 것만 읽음. Evidence Box의 해시 체인은 원리적으로 성립 불가 |
| rate limit | `ratelimit.py` `self._buckets: dict` | 파드당 독립 버킷 → 실효 한도가 레플리카 수만큼 증가. 정책이 조용히 위반됨 |
| circuit breaker | `circuit.py` `self._failures`/`_opened_at` | 파드마다 독립 학습 → `tools/list` 결과가 파드마다 다름 |
| 정책 | `Policy.load` — 기동 시 1회, 핫 리로드 없음 | ConfigMap 변경 시 rollout restart 필요 |
| 백엔드 세션 | `upstream.py` — 백엔드당 세션 1개 + 소유 task | 파드 수 × 백엔드 수만큼 업스트림 연결 증식 |

**면접관이 지금 이 레포에서 볼 수 있는 것:** 잘 짜인 단일 노드 데모. 볼 수 없는 것: 이 사람이 프로덕션 환경에서 무엇을 겪었는지.

## Target User & Narrowest Wedge

- **타깃 (미검증 가설):** 플랫폼/인프라/LLMOps 포지션의 채용담당자·면접관. 레포를 30초 훑고 "인터뷰에 부를지" 판단하는 사람.
- **Narrowest Wedge:** 4주 전체가 아니라 **`docs/k8s-stateful-findings.md` 문서 1개**다. 네 가지 상태 문제 각각의 재현 절차 + 관측 증거 + 결론(수정 또는 기각 근거). 매니페스트는 그 문서의 부속물이다.
- **왜 문서가 wedge인가:** 채용담당자는 yaml을 읽지 않는다. "이 사람이 무엇을 겪고 어떻게 판단했는가"를 읽는다. 네 문제 중 하나(circuit breaker)의 결론이 "고치지 않는 게 맞다"라는 점이 이 문서의 최대 차별점 — 도구를 아는 것과 언제 쓸지 아는 것의 차이를 실물로 보여준다. 이 근육은 `docs/spikes/opa-rego-vs-yaml.md`에서 이미 한 번 발휘됐다.
- **의도적으로 안 하는 것:** OPA 사이드카 분리(P3), 큐 기반 KEDA(P5), vLLM 서빙(P4), compose 경로 변경(P1), Evidence Box 구현(D1 결정).

## Constraints

- 솔로 개발 + 잡서치 병행. 목표 4주, **1주차 말에 이미 제출 가능한 산출물이 있어야 함**(P6).
- 플랫폼: Windows 11 + Docker Desktop. k3d는 WSL2 백엔드 위에서 동작.
- **TLS 인터셉터 환경.** 이미지 빌드에 `certs/windows-roots.crt` + `UV_NATIVE_TLS=1` 패턴이 이미 적용돼 있으며(`gateway/Dockerfile`), k3d의 이미지 pull 경로에서도 유사 문제가 발생할 수 있다.
- GPU 없음 → LLM 서빙(Approach F)은 이 4주 범위 밖.
- **compose 경로를 건드리지 않는다.** `docker-compose.yml`, `scripts/e2e_demo.py`, CI e2e 잡은 그대로 유지 — Evidence Box 파일럿의 "도입 마찰 제로" 포지셔닝이 그 위에 서 있다.
- 기존 97 테스트는 계속 그린이어야 한다. K8s 작업은 `k8s/` 디렉터리 추가 + 필요한 최소 코드 변경으로 한정.

## Premises

세션에서 제시됨 (D2 선택으로 암묵 동의, 명시 이의 없었음):

1. **[P1]** 독자는 채용담당자·면접관이다. 성공 기준은 "돌아간다"가 아니라 "이 사람이 클러스터에서 뭘 겪었는지가 README 30초에 읽힌다". compose 경로는 보존한다.
2. **[P2]** 이 레포의 최대 K8s 자산은 "stateful 서비스를 스케일했더니 조용히 깨졌다"는 실측이다. 튜토리얼 매니페스트가 아니다.
3. **[P3]** OPA 사이드카 분리는 `docs/spikes/opa-rego-vs-yaml.md`의 결정("YAML 유지, OPA 미채택")을 반전시키는 것이다. 이 경로에서는 하지 않는다. 만약 한다면 스파이크 메모를 개정하고 새 논거("K8s에선 정책 배포 경로가 ConfigMap/bundle로 바뀐다")를 대야 한다 — 규모 논거는 여전히 무효다.
4. **[P4]** vLLM은 이 아키텍처에 붙을 자리가 없다. 게이트웨이는 MCP 라우터이며 LLM을 호출하지 않는다. LLM을 호출하는 건 demo-agent 하나뿐이다. LLM serving이 목표라면 별도 축으로 부르고 게이트웨이 스토리와 섞지 않는다.
5. **[P5]** KEDA의 근거는 큐 깊이가 아니라 이미 노출 중인 Prometheus 메트릭(`TOOL_CALLS`, `CALL_DURATION`)이다. 이 시스템은 동기 요청/응답이며 큐가 없다.
6. **[P6]** 이 프로젝트의 실측 이탈률은 100%다. 06-10 설계는 "Week 3가 통상 이탈 지점"이라 썼고, 07-06 설계는 8주간 0줄 구현됐다. 따라서 로드맵은 완주를 전제하면 안 되고, 매주 끝에 독립적으로 제출 가능한 산출물이 남는 구조여야 한다.

## Approaches Considered

### Approach A: Lift-and-Shift Cut — 최소판
compose 6서비스를 그대로 이관. Deployment/Service/Ingress, ConfigMap(`policy.yaml`)·Secret(JWT/ADMIN), probe 3종, `replicas: 1`, kustomize base/overlay.
- Effort: S (human ~1주 / CC ~2일) · Risk: Low
- Reuses: Dockerfile 4종, compose의 env·healthcheck 정의 전부
- Pros: 가장 빠름. 첫 실제 장애물(k3d 이미지 import, TLS 인터셉터)을 여기서 만남
- Cons: `replicas: 1`이면 상태 문제를 하나도 만나지 못함 → **스토리가 생기지 않는다.** 단독 목적지가 아니라 모든 경로의 1주차

### Approach B: Stateful Scale-Out Story ★ 채택 (코어)
A 위에서 의도적으로 `replicas: 3`을 켜서 깨뜨린 뒤, 네 가지를 진단·계측·수정 또는 기각.
- Effort: M (human ~2주 / CC ~4일) · Risk: Med (RWX 볼륨 제약이 실측 전엔 미확정)
- Reuses: 기존 Prometheus 메트릭이 그대로 진단 도구가 됨. 97 테스트가 회귀 안전망
- Pros: 이 레포에서만 나올 수 있는 서사. 네 문제의 답이 각각 다르다는 점이 핵심 — 특히 circuit breaker는 "파드별 유지가 옳다"는 기각 결론이 정답일 가능성이 높음
- Cons: 정답이 미리 정해져 있지 않아 시간 산정이 어려움. audit 공유 방식은 실측 후에야 결정 가능

### Approach C: Platform Engineering Cut
Helm chart(values로 환경 분리) + ArgoCD GitOps + ConfigMap 정책 핫리로드.
- Effort: M (human ~1.5주 / CC ~3일) · Risk: Low
- Pros: 표준적, 안전. "정책 변경이 PR → 머지 → 자동 반영 + audit에 config hash로 기록"은 이 레포 고유 각도
- Cons: Helm/ArgoCD 자체는 지원자 다수가 씀. 차별화 얇음

### Approach D: SRE / Day-2 Operations Cut ★ 채택 (3주차)
OTLP 실배선(`ConsoleSpanExporter` → OTLP → Collector → Tempo/Jaeger), `static_configs` → ServiceMonitor, 장애 주입(`kubectl delete pod`)으로 circuit breaker 실증, graceful shutdown, readiness vs liveness 재정의, KEDA Prometheus 스케일러.
- Effort: M (human ~1.5주 / CC ~3일) · Risk: Low-Med
- Pros: 지금 없는 것(OTLP 파이프라인)을 채우므로 순증 가치. 이미 구현된 circuit breaker를 K8s 환경에서 실증하는 것이라 새 코드가 적음
- Cons: 단독으론 "관측 스택 세팅"으로 읽힐 수 있음 — B의 발견과 묶여야 서사가 됨

### Approach E: Operator / CRD Cut — 창의적·측면
`MCPBackend`(name/url/headers) + `AgentPolicy`(권한 매트릭스) CRD 정의, kopf(Python)로 컨트롤러 구현. reconcile이 ConfigMap 생성 + 게이트웨이 리로드 트리거.
- Effort: L (human ~2주 / CC ~5일) · Risk: Med-High
- Reuses: 레포가 이미 파이썬 워크스페이스라 kopf 추가가 자연스러움. **Evidence Box 스코프 5("`BACKEND_SPECS` 하드코딩 → YAML 설정 일반화")의 K8s-native 형태** — 두 축이 겹치는 유일한 지점이라 파일럿 재개 시 버려지지 않음
- Pros: K8s를 쓰는 게 아니라 확장하는 능력. reconcile loop 경험은 지원자 극소수
- Cons: CRD 설계를 잘못 잡으면(status subresource 없음, reconcile 없는 단순 변환) "yaml을 CRD로 옮긴 것"에 그침. 4주차 스트레치로만 안전

### Approach F: LLM Serving Cut
vLLM Deployment + demo-agent를 자체 서빙으로 전환. GPU 없으면 CPU + 소형 모델.
- Effort: M (human ~1.5주 / CC ~3일) · Risk: Med-High
- Cons 셋 (착수 전 반드시 확인):
  1. 표준 `vllm/vllm-openai` 이미지는 CUDA 기반 — CPU는 별도 빌드/이미지 경로 필요. **착수 전 30분 안에 검증하고, 막히면 llama.cpp server 또는 Ollama로 대체**(K8s 서빙 스토리는 동일하게 성립)
  2. **Qwen2.5-0.5B로는 startupProbe 스토리가 재현되지 않는다** — 수 초면 로드돼 liveness가 죽지 않는다. 겪지 않은 문제를 겪은 것처럼 말하는 것은 면접에서 가장 잘 적발되는 지점
  3. 게이트웨이 스토리와 인과가 없음 (P4)
- **기각(이 4주 범위에서). 별도 축으로 이월** — The Assignment의 JD 실측 결과가 LLM 서빙을 명시 요구하면 그때 착수

## Recommended Approach

**경로 1 = B + D 코어 (사용자 D2 선택, AI 추천과 일치).** A는 1주차로 흡수, C 또는 E는 4주차 택1.

### 1주차 — 올리고, 깨뜨린다
- k3d 클러스터 생성 **(워커 노드 2개 이상: `k3d cluster create agentops --agents 2`)**. 단일 노드면 RWX 볼륨 제약이 드러나지 않아 2주차 audit 문제가 반쪽이 된다.
- 이미지 4종 빌드 + `k3d image import` (또는 k3d 내장 레지스트리). TLS 인터셉터 이슈가 여기서 재현될 수 있음
- Deployment/Service 6종, Ingress(gateway + grafana), ConfigMap(`policy.yaml`), Secret(`GATEWAY_JWT_SECRET`/`ADMIN_TOKEN`), probe 3종
- **검증 1:** `scripts/e2e_demo.py`를 클러스터 밖에서 Ingress 경유로 실행 → 성공-성공-거부 시나리오 통과
- **`replicas: 3`으로 올리고 무엇이 깨지는지 관찰·기록** (수정은 2주차)
- **주말 산출물:** `docs/k8s-stateful-findings.md` 초안 — 재현 절차 + 증상. 여기서 멈춰도 제출 가능한 물건이 있다

### 2주차 — 네 가지를 하나씩 결론낸다
각 항목: 재현 → 관측 증거 → 선택지 비교 → 결론(수정 또는 기각 근거).

| 항목 | 선택지 | 결정 기준 |
|---|---|---|
| MCP 세션 | `stateless=True` 전환 / `sessionAffinity: ClientIP` / Ingress 어피니티 | stateless로 가면 무엇을 잃는가를 명시. 어피니티는 파드 재시작 시 동작을 실측 |
| audit | PVC(RWX) / StatefulSet+파드별 파일 / 사이드카 수집 | **k3d local-path는 RWO만 제공** — RWX가 없으면 어떤 대안을 택했는지가 곧 서사 |
| rate limit | 분산 저장(Redis) / 한도를 레플리카 수로 나눔 / 게이트웨이 앞단 이동 | 뒤 둘은 **코드 변경 0** — 인프라로 푸는 게 나은 경우의 예시로 문서화 |
| circuit breaker | 공유 / **파드별 유지 + 기각 근거** | 파드마다 자기 연결의 건강을 판단하는 게 옳다는 논증. 네 개 중 유일하게 "안 고침"이 답일 가능성이 높은 항목 |

- **주말 산출물:** findings 문서 완성. 이 경로의 핵심 산출물

### 3주차 — 운영한다 (Approach D)
- **OTLP 실배선**: `observability.py`의 `ConsoleSpanExporter` → OTLP exporter(env로 endpoint 주입) → OTel Collector → Tempo 또는 Jaeger. audit의 `trace_id`로 실제 조회 가능해야 함
- `static_configs` → **ServiceMonitor**(kube-prometheus-stack). 레플리카 3개가 자동 발견되는지 확인
- **장애 주입**: `kubectl delete pod ticket-server-*` → circuit breaker open을 Grafana에서 관측 → `tools/list`에서 `ticket__*` 소거 확인. 이미 구현된 기능의 K8s 환경 실증
- **graceful shutdown**: `terminationGracePeriodSeconds` + preStop + SIGTERM 처리. in-flight `tools/call` 중 파드 삭제 시 완주하는지 중단되는지 **실측 기록** (코드만 봐선 `lifespan` 종료와 진행 중 호출의 경합이 확정되지 않음)
- **readiness vs liveness**: 현재 `/health`는 무조건 `{"status":"ok"}`. "백엔드 0/3 연결된 게이트웨이는 ready인가?"에 답하고 `/ready` 분리 여부 결정
- **KEDA**: Prometheus 스케일러로 `CALL_DURATION` p99 또는 요청률 기반 스케일 (P5)

### 4주차 — 택1 (3주차 말에 결정)
- **C (안전):** Helm chart + ArgoCD. 각도는 "권한 매트릭스 변경이 PR → 머지 → 자동 반영 + config hash가 audit에 기록"
- **E (희소):** kopf로 `MCPBackend`/`AgentPolicy` CRD + 컨트롤러. status subresource와 실제 reconcile이 있어야 진짜

**근거:** B는 이 레포에서만 나올 수 있고, D는 지금 비어 있는 OTLP 구멍을 채우면서 이미 구현된 resilience를 실증한다. 1주차 말에 이미 findings 초안이 남으므로 P6(이탈률 100%)를 구조적으로 방어한다. 매주 말 독립 산출물이 있다.

## The Assignment

**코드보다 먼저, 1주차와 병행해서: 타깃 포지션 JD 5건을 모아 요구사항을 실제로 세어라.**

07-06 문서에서 "실서비스 경로는 코드가 아니라 첫 대상 회사와의 대화"였던 것과 정확히 같은 구조다. 이번 트랙의 "고객"은 채용담당자이고, 지금 그 수요 증거는 0이다. "LLMOps 성향 JD에서 요구하는 조합 그대로"는 이 세션에서 검증되지 않은 진술이다.

한 시간이면 된다. 실제로 지원할 회사 5곳의 JD를 열고, 다음을 세어라:

1. K8s를 **필수**로 적은 곳이 몇 곳인가 (우대와 필수를 구분해서)
2. **LLM 서빙**(vLLM/TGI/추론 최적화)을 적은 곳이 몇 곳인가 — 이게 Approach F를 별도 축으로 착수할지의 유일한 근거다
3. **관측성**(OTel/Prometheus/트레이싱)을 적은 곳이 몇 곳인가 — 이미 구현했으므로 K8s 승격만 하면 되는 항목
4. 그 외에 반복 등장하는데 이 레포에 **없는** 것은 무엇인가

4번이 가장 중요하다. 없는 것이 K8s가 아니라 다른 것(예: Terraform, 특정 클라우드, 데이터 파이프라인)이라면 이 4주 계획 자체를 재배치해야 한다. 4주를 태우기 전에 한 시간으로 검증할 수 있는 것을 검증하지 않는 것이 지금 가장 큰 리스크다.

부수 효과 하나 더: JD 5건을 읽으면 findings 문서를 **누구를 향해 쓰는지**가 구체화된다. "채용담당자"는 카테고리이고, "이 다섯 공고를 낸 팀"은 사람이다.

## What I noticed about how you think

- 당신이 가져온 제안의 첫 문장이 "새 프로젝트 파지 말고 지금 만들고 있는 걸 K8s에 올리는 게 가장 적합해요"였다. 그리고 그 근거로 "튜토리얼용 todo 앱 마이크로서비스 데모는 시간 낭비고 면접에서 스토리 가치도 없음"을 댔다. 대부분은 새 걸 시작한다 — 새 레포가 진도감을 주니까. 기존 자산을 레버리지하겠다는 판단은 진도감이 아니라 결과를 보는 사람의 것이다.
- 주차별 로드맵에 "핵심 개념" 열을 따로 뒀다. 할 일이 아니라 배울 것을 열로 뽑았다는 뜻이다. 06-10 세션에서 "권한 매트릭스 하나가 프로젝트 전체의 뼈대"라고 썼던 것과 같은 습관 — 작업 목록보다 구조를 먼저 정의한다.
