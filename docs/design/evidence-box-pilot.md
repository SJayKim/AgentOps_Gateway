## Problem Statement

4주 데모 시스템(S1–S6 + stretch, 97 테스트 그린)은 완성됐고, 원 설계의 전제 1("실서비스 경로는 코드가 아니라 첫 대상 회사와의 대화")에 따라 보류돼 있던 The Assignment가 실행됐다. 보안/플랫폼 담당자와의 대화에서 고통이 확인됐다: **수동 크리덴셜 관리 + tool 단위 감사 부재**. `docs/design/agentops-gateway-design.md` § Wedge Kill Criterion의 3기준 중 **"재검토 착수"** 칸에 해당한다.

이제 문제는 "데모를 어떻게 더 큰 서비스 기준으로 확장하느냐"인데, 이 세션의 결론은 확장의 1차 관문이 멀티테넌시·HA 같은 인프라 스펙이 아니라 **그 회사 환경에 실제로 깔리는 파일럿 1개**라는 것이다. 이를 위해 데모를 "감사 증거 어플라이언스(Evidence Box)"로 완성한다.

## Demand Evidence

- **실측 1건 (0 → 1):** 대상 회사의 보안/플랫폼 담당자와 The Assignment 대화 실행. "수동 크리덴셜 관리 + tool 단위 감사 없음" 카테고리의 고통을 직접 확인. 고통의 주인은 원 설계의 가설 타깃("도구 접근을 통제할 방법이 없어 에이전트 도입을 보류시키는 보안/플랫폼 담당자")과 일치 — 가설이 실측으로 승격됨.
- **Kill criterion 판정:** "재검토 착수" 조건(수동 크리덴셜 + 감사 없음으로 고통) 충족. wedge(거버넌스 증거 계층) 재검토가 정당해짐.
- **증거의 한계 (정직하게 기록):** ① 담당자 이름·직함·발언 원문 미기록 ② 그 회사의 현재 워크어라운드와 그 비용(시간/인력/리스크) 미확인 — 대화가 거기까지 가지 않았음. 이 두 공백은 The Assignment 2차 대화(아래)의 1순위 수집 항목이다.
- **시장 반증 겸 보강:** 2026년 현재 MCP gateway/에이전트 거버넌스 제품이 10개 이상 존재함에도 이 구매자는 아무것도 도입하지 않고 수동 크리덴셜로 버티고 있다. 수요는 있으나 기존 공급이 닿지 않는다는 신호.

## Status Quo

- **대상 회사 수준: 미확인.** 수동 크리덴셜 관리라는 카테고리만 확인. 구체 워크플로우(키 공유 방식, 회수 절차, 감사 요청 시 대응)와 비용은 2차 대화에서 채운다. 채우기 전까지 확장 투자는 "파일럿 배포 가능 최소"로 캡한다(전제 4).
- **시장 수준 (2026-07 웹 검색):** MCP gateway 카테고리는 상품화 완료 — IBM ContextForge 1.0 beta(높은 운영 복잡도, 상용 지원 없음, 관측 빈약으로 기록됨), Microsoft MCP Gateway, Docker, Zapier 등. 감사/거버넌스 포지셔닝도 이미 존재 — Lunar.dev MCPX(불변 감사 로그), MintMCP(컴플라이언스·감사 추적), Lasso(보안 관측), Drata(tamper-evident 에이전트 증거, 컴플라이언스 대기업의 진입). Linx가 정리한 CISO 요구는 이 세션에서 확인된 고통과 같은 언어다: 사람 신원에 귀속되는 감사 추적, tool 단위 강제, 실시간 차단.
- **함의 (세션 eureka):** 판이 붐비는데 구매자는 아무것도 안 쓴다 = 기술 공백이 아니라 **도입 마찰 공백**. 엔터프라이즈 SaaS는 조달·데이터 반출 장벽에, ContextForge는 운영 복잡도에 막힌다. 진짜 경쟁자는 그 회사의 임시방편이고, 이기는 방법은 기능 표가 아니라 도입 형태다.

## Target User & Narrowest Wedge

- **타깃 (실측 승격):** 에이전트 도입을 통제 문제로 보류/제한 중인 보안/플랫폼 담당자. 조직에서 이 사람이 파는 것은 "증거"다.
- **Wedge: Evidence Box — 감사 증거 계층** (원 설계 Approach C의 부활, 이번엔 AI 권고가 아니라 실측 근거).
  - append-only audit + **해시 체인** (아래 위협 모델 참조 — 리포트에 박힌 체인 헤드 대비 사후 무결성 검증)
  - **사람 신원 귀속**(agent 뒤의 human owner까지)
  - "지난 24h 누가 민감 tool에 접근 시도했나" 리포트 + 거부 증거(거부된 `agent:server:tool` 식별자와 사유)
  - **증거 리포트 생성기**(보안 담당자가 위에 보고할 물건)
  - 차별화는 기능이 아니라 **도입 형태**: self-hosted, 데이터 반출 없음, 조달 불필요, 설치→첫 리포트 30분
- **의도적으로 안 하는 것:** 크리덴셜 브로커(전제 3, 조건부 2단계), 멀티테넌시/HA/수평확장(전제 1), 기능 표 경쟁(전제 2), shadow 모드(2차 대화 게이트 뒤 — Open Questions 5).
- **Wedge Kill Criterion 상태 갱신:** repo 설계 문서의 3기준 중 "재검토 착수" 발동(2026-07-06 세션). 다음 판정 지점은 2차 대화 — 파일럿 거절 + 크리덴셜 우선 답변이면 wedge 형태 재조정(아래 Open Questions).

## Constraints

- 솔로 개발. 기존 코드베이스(FastAPI gateway, default-deny YAML 정책엔진, audit JSONL, admin 페이지, OTel/Prometheus/Grafana, docker compose) 위에 증분으로만 얹는다.
- 구현 투자 상한: **파일럿 배포 가능 최소** (전제 4). 2차 대화 전에 그 이상 선행 투자 금지.
- 파일럿 형태 제약: 상대 인프라 안에서 self-hosted로 구동, 데이터가 그 서버 밖으로 나가지 않음. 이 제약 자체가 제품 포지셔닝이다.
- **Upstream 연결 제약 (현재 코드 기준):** gateway는 무인증 Streamable HTTP upstream만 지원한다(`gateway/src/gateway/upstream.py` — auth 헤더·stdio·SSE 미지원). 파일럿 컷은 정적 헤더 인증까지만 확장하고(아래 스코프 5), stdio 기반 사내 MCP 서버는 명시적 미지원 — 2차 대화에서 상대 서버의 transport·인증 방식을 반드시 확인한다.
- 단일 프로세스/단일 워커 전제(현행 compose 기본). 해시 체인의 last-hash 직렬화는 이 전제 위에서만 성립하며, 멀티 워커 전환은 범위 밖.
- 원 설계의 포트폴리오 가치(관측성 스택·커리어 축)는 유지 — kill 대상 아님 (kill criterion 적용 범위 그대로).

## Premises

세션에서 합의됨 (P3는 Codex 반박 수용으로 조건부 수정):

1. **[P1]** 확장의 1차 관문은 멀티테넌시·HA가 아니라 그 회사 환경에 깔리는 파일럿 1개다. Out of Scope였던 인프라 항목들은 파일럿 생존 후에만 순서가 온다.
2. **[P2]** wedge는 감사 증거 계층이고, 차별화는 기능이 아니라 도입 마찰 제로(self-hosted, 데이터 반출 없음, 조달 불필요, 며칠 안 가치)다. MintMCP/Drata/Lunar와 기능 표로 싸우지 않는다.
3. **[P3 — 조건부]** 크리덴셜 브로커는 기본 2단계다. 단, 2차 대화에서 구매자가 "크리덴셜 처리 없이는 파일럿 안 한다"고 답하면 순서를 재편한다. 2차 대화 질문지에 이 검증 항목을 명시적으로 포함한다.
4. **[P4]** 다음 검증 관문은 2차 대화(파일럿 제안)다. Q2 공백(현재 워크어라운드 + 비용)을 거기서 채우고, 그 전까지 구현 투자는 파일럿 배포 가능 최소로 캡한다.

## Cross-Model Perspective

Codex(gpt-5.5, read-only, 세션 대화 비공개 콜드 리드) 2차 의견 — 2026-07-06:

- **Steelman:** "에이전트 도구를 도입 중이지만 풀 gateway나 크리덴셜 브로커를 신뢰할 준비가 안 된 보안/플랫폼 팀을 위한 self-hosted MCP 감사 증거 어플라이언스. 조달·데이터 반출·기존 환경 교체 없이, 며칠 안에 귀속 가능한 tool 단위 접근 증거와 감사용 리포트를 제공한다."
- **가장 드러나는 답변:** "10개 이상 제품이 존재하는데 확인된 구매자는 아무것도 안 쓴다" — 제품은 '더 나은 gateway'가 아니라 '무관리 상태에서 신뢰 가능한 보안 증거까지의 최저 마찰 경로'여야 한다. 킬러 기능은 도입 형태다.
- **P3 반박:** 확인된 고통의 절반이 크리덴셜인데, 그 비용이 주로 키 로테이션/공유/회수 노동이라면 감사만으론 "진짜 상처 위의 대시보드"가 된다. 반증 조건: 2차 대화에서 "주간 고통은 크리덴셜 관리이고, 그것 없이는 파일럿 안 한다"는 답. → **세션 수용: P3를 조건부로 수정.**
- **48시간 프로토타입 제안:** 기존 FastAPI gateway 위 "MCP Evidence Box" — 사람 신원 귀속(JWT claim), 민감 tool 분류(YAML), 거부 증거, admin 증거 뷰 + CSV/JSONL export, 리포트 생성기(config hash + audit 해시 체인), compose 원커맨드. 스킵: 멀티테넌시/HA/크리덴셜 브로커/과금. 목표: 2차 대화를 "MCP 서버 1개 + 에이전트 2개 주시면 이번 주에 당신 환경의 증거를 보여드린다"로 끝내는 것. → **Recommended Approach에 채택.**

## Approaches Considered

### Approach A: Evidence Box 파일럿 컷 ★ 선택됨
- 기존 gateway 위에 증거 어플라이언스 완성: 사람 신원 귀속, audit 해시 체인, 증거 리포트 생성기, admin 증거 뷰 확장(민감 tool 분류/24h 뷰/export), 백엔드 config 등록(현재 `app.py` `BACKEND_SPECS` 3종 하드코딩 → 설정 일반화 + 정적 헤더 인증), 배포 패키징(compose + 컨테이너 이미지 + 설치 문서).
- Effort: S-M (human ~1-2주 / CC ~2-4일) · Risk: Low-Med
- Reuses: gateway 코어, 정책엔진, audit JSONL, admin 페이지, compose 전부.
- Pros: 2차 대화 물건이 최단 거리. P4 투자 캡과 일치. "증거" 주장을 실물(해시 체인·귀속·리포트)로 만듦.
- Cons: 실환경 운영 요건(TLS, 로그 보존, 업그레이드)은 파일럿 중 대응. 크리덴셜 고통 미해소(조건부 P3에 의한 의도).

### Approach B: Evidence Box + 싱글테넌트 운영 성숙
- A 전부 + TLS/리버스프록시 가이드, secret 관리 정리, audit 로그 로테이션·보존, 업그레이드 경로, fail-closed 정책 명시.
- Effort: L (human ~4주 / CC ~1-2주) · Risk: Med
- Pros: 파일럿→상시 운영 전환 매끄러움. 기술 신뢰 신호 최대.
- Cons: 2차 대화 결과를 못 보고 수 주 선행 투자. 요구사항 절반이 추측. "멀티테넌시만 뺀 작은 풀 플랫폼" 함정. **기각 사유: P4 투자 캡 위반.**

### Approach C: Shadow Observer 우선
- 강제 없이 기록만 하는 shadow 모드로 최소 마찰 설치, 이후 enforce 승격.
- Effort: S (human ~1주 / CC ~2-3일) · Risk: Low(도입)/Med(가치 전달)
- Pros: 파일럿 승인 문턱 최저. 보안 제품의 검증된 도입 패턴.
- Cons: 핵심 차별화(실시간 거부 증거)가 시뮬레이션으로 약해짐. 기존 로깅과 차별 흐림. **기각(단독 경로로는). shadow 모드 자체도 2차 대화에서 상대가 "강제부터는 부담"이라 답할 때만 착수하는 조건부 항목으로 이월(Open Questions 5) — 크리덴셜 브로커와 같은 게이트 논리.**

## Recommended Approach

**Approach A (Evidence Box 파일럿 컷)** — 스코프 6항목:

1. **사람 신원 귀속**: JWT claim `{agent_id, exp}` → `{agent_id, owner, exp}` 확장(예: `owner: j.park@corp`). **호환성 결정: owner 없는 토큰은 계속 유효하며 증거 뷰·리포트에 `unattributed`로 표기** — 기존 토큰·테스트 픽스처를 깨지 않는다. 단 토큰 발급 스크립트는 owner를 필수 인자로 받도록 갱신(파일럿 발급분은 전원 귀속). audit 레코드에 owner 필드 추가.
2. **audit 해시 체인**: JSONL 각 레코드에 `prev_hash`(SHA-256) 연결 + 오프라인 검증 커맨드 `verify_audit`.
   - **위협 모델 (증명하는 것/못 하는 것):** 체인은 "리포트에 박힌 체인 헤드 시점 이후, 기록된 레코드가 수정·삭제·삽입되지 않았음"의 사후 검증을 제공한다(외부 앵커 = 리포트/번들에 기록된 체인 헤드). 서명 키가 없으므로 **파일 쓰기 권한을 가진 공격자의 전체 재작성은 막지 못하며**(앵커된 헤드와의 불일치로만 탐지), 애초에 기록되지 않은 이벤트의 완전성도 증명하지 못한다. 이 한계는 리포트 문구에도 명시한다.
   - **꼬리 절단**: 체인 헤드 앵커와의 대조로 검출 — SC2 테스트에 중간 변조와 꼬리 절단 케이스를 모두 포함. **앵커 창 경계**: 마지막 앵커(가장 최근 리포트/번들) 이후에 추가된 레코드는 다음 앵커 전까지 꼬리 절단 검출 범위 밖이다 — 보호 창은 리포트 생성 주기가 정의하며, 이 한계도 리포트 문구에 명시한다.
   - **audit 쓰기 실패 정책**: 현행 "가용성 우선(쓰기 실패해도 호출 진행)" 유지하되, 쓰기 실패 카운터를 메트릭·리포트에 노출("audit write failures: N") — 완전성 공백을 숨기지 않는다. fail-closed 모드는 파일럿 피드백 후 검토.
   - **제네시스 규칙**: 기존 무해시 audit 파일은 아카이브하고 새 체인을 시작(마이그레이션 없음). 단일 프로세스 전제(Constraints 참조).
3. **증거 리포트 생성기**: CLI `generate_report --since --until` + admin 페이지 다운로드 버튼. Markdown/HTML 출력, 구조는 다음 6블록(승인된 와이어프레임 `~/.gstack/projects/SJayKim-AgentOps_Gateway/designs/mockup-20260706/evidence-report-wireframe.{html,png}` — 본 개정판 어휘로 재생성됨 — 는 블록 배치 참조용이며, 셀 값·명칭·스탯 항목은 본문 스펙이 우선한다):
   ① 헤더 — 기간·생성시각·policy config hash·audit 체인 헤드·검증 상태 배지
   ② 요약 스탯 — **audit decision enum 그대로**: `allowed / denied / auth_failed / rate_limited / error` + 민감 tool 접근 수. auth_failed는 보안 구매자용 헤드라인 항목
   ③ 민감 tool 접근 최근 24h 표 — time, human owner(agent보다 앞 열), agent, server__tool, decision, trace ID
   ④ 거부 상세 — 거부된 `agent:server:tool` 식별자(예: `support-agent:ops:query_logs`), 사유(default-deny로 매칭 룰이 없어 거부된 경우 "default-deny: 미기재 조합" 명기, 인자 정책 위반은 해당 detail), 건수
   ⑤ 사람/에이전트별 접근 분해
   ⑥ export — CSV/JSONL + **verified bundle**(.tar.gz — audit JSONL + 체인 헤드 + config hash 동봉. **서명 아님**: 키 도입 없이 검증 가능한 참조 묶음. 명칭도 "signed"가 아닌 "verified"로)
4. **민감 tool 분류 + admin 증거 뷰**: 정책 YAML 최상위 예약 키 `_sensitive:`(fnmatch 글롭 목록, 예: `ops__*`)로 정의 — **`Policy.load`가 agent 파싱 전에 예약 키를 분리하는 로더 스키마 변경임을 명시**(현행 로더는 최상위 키 전부를 agent로 취급하므로 그냥 추가하면 `warn_unknown_tools`에서 죽는다). admin 페이지에 24h 민감 접근/거부 뷰 + export 버튼.
5. **백엔드 설정 등록 + upstream 인증**: `BACKEND_SPECS` 하드코딩을 **YAML 설정 파일**(형식 확정: 정책과 동일하게 YAML)로 일반화 — `{name, url, headers?}` 목록. `headers`로 정적 헤더 인증(예: `Authorization: Bearer …`) 지원. 임의 Streamable HTTP MCP 서버 1개를 코드 수정 없이 등록하는 통합 테스트로 증명. stdio 미지원 명시.
6. **배포 패키징**: 컨테이너 이미지(GHCR) + 상대 환경용 docker compose + 설치 문서. 설치 문서 체크리스트에 반드시 포함: ① **실 secret 생성·주입 절차**(`GATEWAY_JWT_SECRET` 32바이트 이상 랜덤 생성, `ADMIN_TOKEN` — 데모 secret `demo-secret-do-not-use-in-prod` 금지 명시) ② **admin 페이지 노출 가이드**(내부망/localhost 바인딩 전용, 데모 수준 인증임을 고지) ③ 스모크 시나리오 스크립트(동봉 데모 트래픽 — "첫 리포트"가 빈 문서가 되지 않게 함). "설치→첫 리포트 30분"은 이 스모크 시나리오 완주 기준.

핵심 데모 장면 유지: 실시간 POLICY_DENIED + LangGraph 우회 데모는 enforce 모드의 세일즈 장면으로 그대로 활용. (`would_deny` 등 shadow 관련 decision 값 추가는 shadow 착수 시점에 enum·메트릭 라벨·admin 필터를 한 커밋에서 갱신 — `rate_limited` 필터 누락 전례의 재발 방지.)

## Open Questions

1. **[2차 대화에서 채울 것]** 그 회사의 현재 워크어라운드와 비용(주당 시간, 담당 인원, 감사 요청 대응 방식). 담당자 직함과 발언 원문.
2. **[P3 조건 판정]** "증거만으로 파일럿 가능한가, 크리덴셜 처리가 필수인가?" — 후자면 크리덴셜 브로커를 wedge에 편입하고 본 문서 개정.
3. **[파일럿 성공 기준 협의]** 상대가 "가치 있다"고 판정하는 조건이 뭔가 — 리포트 1장? 감사 대응 1회? 도입 승인 근거?
4. **[파일럿 환경 확인]** 연결 대상 MCP 서버의 transport(Streamable HTTP인가, stdio인가)와 인증 방식 — stdio면 파일럿 전 어댑터 추가 판단 필요(현재 미지원).
5. **[shadow 모드 필요성]** 상대가 "강제부터는 부담"이라 답하면 그때 착수(조건부 이월 항목). 범위는 policy 거부 결정만 — auth 실패·rate limit은 shadow에서도 실제 동작.
6. 파일럿 이후 유료 전환의 형태(라이선스? 지원 계약?) — 파일럿 결과 전 결정하지 않음.

## Success Criteria

구현(각각 테스트로 검증):
1. JWT `owner` claim이 audit 레코드·admin 뷰·리포트에 끝까지 흐르고, owner 없는 토큰은 `unattributed`로 표기 — e2e 테스트.
2. `verify_audit`가 정상 로그 PASS / **중간 레코드 변조 FAIL / 꼬리 절단 FAIL**(리포트 체인 헤드 대조)을 판정 — 각각 테스트.
3. `generate_report`가 7일치 audit에서 위 6블록 구조의 MD/HTML 생성 — config hash·체인 헤드 포함, 스탯은 `allowed/denied/auth_failed/rate_limited/error` enum 그대로.
4. `_sensitive:` 글롭 분류가 admin 24h 뷰와 리포트에 반영, CSV/JSONL/verified bundle export 동작. 로더 스키마 변경 후 기존 정책 파일 로드 회귀 테스트 통과.
5. 데모 3종 외 신규 Streamable HTTP MCP 서버 1개를 코드 수정 없이(YAML 설정만으로, 정적 헤더 포함) 등록해 라우팅·정책·audit이 작동 — 통합 테스트.
6. audit 쓰기 실패 카운터가 메트릭·리포트에 노출 — 실패 주입 테스트.
7. 클린 환경에서 문서만 보고 docker compose 설치→동봉 스모크 시나리오→첫 리포트 생성까지 30분 이내 — 셀프 실측 1회(작성자 실측은 프록시임을 인정. 가능하면 제3자 1회 추가).

검증(코드 밖, 이 문서의 진짜 관문):
8. 2차 대화 실행 — Open Questions 1·2·3·4 수집 + 파일럿 ask 전달("MCP 서버 1개 + 에이전트 2개 주시면 이번 주에 당신 환경의 증거를 보여드립니다").
9. 파일럿 합의(구두라도) 또는 명시적 거절 — 거절 사유가 kill criterion 다음 판정의 입력.

## The Assignment

**구현보다 먼저 잡을 것: 같은 담당자와 2차 대화 일정.** 대화 목표는 네 가지, 이 순서로 —

1. **현상 재구성 (Q2 공백):** "지금은 에이전트/키 관리를 실제로 어떻게 하세요? 마지막으로 감사 기록이 필요했던 때가 언제였고, 뭘 냈어요?" — 워크어라운드와 비용을 숫자로. 직함과 원문을 이번엔 기록해 올 것.
2. **P3 조건 판정:** "접근 기록·증거가 먼저 필요하세요, 아니면 키 관리 자동화 없이는 의미가 없나요?"
3. **파일럿 환경 확인:** "그 MCP 서버(또는 붙일 도구)는 HTTP로 노출돼 있나요, 프로세스로 띄우나요? 인증은요?" (Open Questions 4 — stdio면 파일럿 컷 조정)
4. **파일럿 ask:** "내부 MCP 서버 1개랑 에이전트 2개만 지정해 주시면, 이번 주 안에 당신 환경 안에서 접근 증거 리포트를 보여드릴게요. 데이터는 서버 밖으로 안 나갑니다." — 승낙이면 Success Criteria 8·9 충족, 거절이면 사유가 다음 kill criterion 판정 입력.

구현(Recommended Approach 1–6)은 이 일정이 잡힌 뒤 대화 전까지의 기간에 맞춰 진행한다 — 대화가 다음 주면 전부, 내일이면 리포트 생성기(3)만 먼저.

## What I noticed about how you think

- D1에서 내 권고(커리어/포트폴리오)를 보고도 "스타트업/실서비스"를 골랐다. 이유는 다음 질문에서 드러났다 — The Assignment를 이미 실행하고 온 상태였다. 권고를 기각할 근거를 세션 밖에서 만들어 오는 패턴은 6/10 세션(AI 권고 C 기각, B 선택)과 같다. 이번에도 그 선택이 옳았다.
