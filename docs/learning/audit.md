# 학습 자료: `Audit 로그` 완전 해부

> 대상: `gateway/src/gateway/audit.py`
> 목적: 모든 tool 호출을 변조 불가능한 한 줄짜리 기록으로 남겨, "누가 무엇에 접근을 시도했고 어떤 판정을 받았나"를 사후에 신뢰할 수 있게 보존하는 거버넌스 증거 계층을 이해한다.

## 0. 큰 그림

### 흐름 다이어그램

```
 에이전트 ─ tools/call 요청 ─▶ Gateway
                                  │
                  ┌───────────────┼───────────────┐
                  │               │               │
              JWT 인증         YAML 정책        백엔드 호출
                  │               │               │
                  └──── decision 1개로 확정 ───────┘
                       allowed / denied / auth_failed / error
                                  │
                                  ▼
                       record(...)  ← audit.py
                                  │
                       {ts, agent, tool, args_summary,
                        decision, trace_id}  ← JSON 1줄
                                  │
                                  ▼  open(path, "a")  (append 전용)
                       ┌──────────────────────────┐
                       │ audit/audit.jsonl        │
                       │ {...}\n   ← 줄 1          │
                       │ {...}\n   ← 줄 2          │
                       │ {...}\n   ← 줄 3 (덮지 않음)│
                       └──────────────────────────┘
                                  │
                                  ▼
                       S6 admin 페이지가 직접 읽음
```

### 내러티브 (메타포: 건물 출입 기록 대장 / 비행기 블랙박스)

Gateway를 출입 통제가 있는 건물이라고 생각해 보자. 에이전트(방문자)가 어떤 도구(방)에 들어가려고 할 때마다, 경비 데스크는 **인증(신분증 확인) → 정책(이 사람이 이 방에 들어가도 되나) → 실제 안내**라는 절차를 밟는다. 그리고 그 결과가 무엇이든 — 들여보냈든(`allowed`), 막았든(`denied`), 신분증이 가짜였든(`auth_failed`), 안내 도중 사고가 났든(`error`) — 경비는 **반드시 출입 기록 대장에 한 줄을 적는다**. `audit.py`가 바로 이 출입 기록 대장을 펜으로 적는 손이다.

이 대장에는 중요한 규칙이 하나 있다. **이미 적은 줄은 절대 지우거나 고치지 않는다.** 새 줄을 맨 아래에 덧붙이기만 한다(append-only). 그래서 이 파일은 비행기의 블랙박스처럼 "사후에 신뢰할 수 있는 사실의 기록"이 된다. 누군가 나중에 "그 에이전트가 정말 운영 로그에 손대려 했나?"를 따질 때, 이 대장이 변조 없이 그 시도를 증언한다. 설계 문서(design.md 전제 4)가 "정책 거부 + audit log"를 가장 설득력 있는 산출물로 꼽은 이유가 여기 있다 — 거부 장면 자체보다, 그 거부가 영구히 기록으로 남는다는 사실이 거버넌스의 핵심 가치다.

마지막으로 이 손에는 철학이 하나 더 있다. **대장에 적다가 펜이 부러져도(디스크 오류 등), 방문자를 막지는 않는다.** 기록 실패는 에러 로그만 남기고 호출은 그대로 진행시킨다. 데모 기준에서는 "가용성 > 감사 완결성" — 기록을 못 남겼다는 이유로 정상 요청을 거부하면 손해가 더 크기 때문이다.

### 레코드 필드 표

| 필드 | 값 예시 | 무엇 | 왜 |
|---|---|---|---|
| `ts` | `"2026-06-15T07:21:03.123+00:00"` | UTC ISO8601 타임스탬프 | admin 페이지 시간 필터의 기준이 되는 단일 시계 |
| `agent` | `"docs-bot"` 또는 `"anonymous"` | 호출한 에이전트 ID | "누가" 시도했나 |
| `tool` | `"ops__query_logs"` | prefix 포함 전체 도구 이름 | "무엇에" 접근했나. admin이 prefix(`ops__`)로 서버를 도로 추출 |
| `args_summary` | `'{"q":"error"}'` (최대 256자) | 인자 전체 JSON을 256자에서 절단 | "어떻게" 호출했나. 로그 비대화·민감정보 과다기록 방지 |
| `decision` | `"allowed"` / `"denied"` / `"auth_failed"` / `"rate_limited"` / `"error"` | 5종 판정 enum | 통제의 결과. 메트릭과 어휘 공유 |
| `trace_id` | `"a1b2...32hex"` | OTel trace ID (32 hex) | 게이트웨이 로그·span과 같은 값 → 교차 추적 |

## 1. `audit.py` — 역할

### 배경: 왜 append-only JSONL인가, 왜 기록 실패가 호출을 막지 않는가

파일 상단 docstring이 세 가지 핵심 설계 결정을 직접 밝히고 있다. 그대로 인용한다.

```python
"""audit log — append-only JSONL. 한 번 쓴 줄을 수정·삭제하는 코드 경로가 아예 없다.

[왜 append-only JSONL인가]
감사 로그의 가치는 "누가 무엇에 접근을 시도했나"를 사후에 신뢰할 수 있게 보존하는 것이다
(design.md 전제 4: 거부 + audit log가 가장 설득력 있는 산출물). 수정·삭제 경로가 없는
append-only 파일이면 그 자체로 "변조 안 됨"의 약한 보증이 되고, DB·인덱스 없이 한 줄씩
append만 하면 돼서 구현이 단순하다. admin 페이지(S6)도 이 파일을 직접 읽는다.

[decision enum을 메트릭과 공유하는 이유]
decision은 allowed | denied | auth_failed | rate_limited | error 5종 — observability.py
메트릭의 라벨과 정확히 동일하다 (eng review 이슈 2). 감사 로그와 메트릭이 같은 어휘로 같은
사실을 기록해야, 대시보드의 "거부 12건"과 audit의 "denied 12줄"이 어긋나지 않는다.
(rate_limited는 S5 stretch rate limiting이 더한 값 — ratelimit.py 참조.)

[기록 실패 시 호출을 막지 않는 이유]
디스크 오류로 audit 쓰기가 실패해도 tool 호출 자체는 진행시킨다(에러 로그만 남김).
데모 기준에선 가용성 > 감사 완결성 — 감사 못 남겼다고 정상 요청을 거부하면 손해가 더 크다.
"""
```

- **왜 append-only JSONL인가?** 감사 로그의 가치는 "변조 불가능한 사후 증거"다. 수정·삭제 코드 경로가 아예 없는 파일이면 그것만으로 "변조 안 됨"의 약한 보증이 된다. 게다가 JSONL(줄마다 JSON 1개)은 DB도, 인덱스도, 스키마 마이그레이션도 필요 없다 — 한 줄씩 끝에 붙이기만 하면 된다. 데모 시스템에 딱 맞는 최소 구현이다. 스펙(`04-auth-policy-audit.md`)이 요구하는 "append-only JSONL, 모든 tools/call에 1줄"을 그대로 만족한다.

- **왜 기록 실패가 호출을 막지 않는가?** 두 가지 가치가 충돌할 수 있다 — (1) 모든 호출을 빠짐없이 기록하는 **감사 완결성**, (2) 정상 요청은 정상 처리하는 **가용성**. 디스크가 가득 차거나 권한이 없어 기록이 실패할 때, 이 코드는 가용성 손을 든다. 감사를 못 남겼다고 멀쩡한 요청을 거부하면 사용자 손해가 더 크다는 데모 기준의 판단이다. 대신 실패 사실은 에러 로그로 흔적을 남긴다.

### 줄별 해설 — import와 모듈 준비

```python
import json
import logging
from datetime import datetime, timezone
from pathlib import Path

logger = logging.getLogger(__name__)
```

- **의미**: `json`으로 레코드를 직렬화, `logging`으로 기록 실패를 알림, `datetime/timezone`으로 UTC 타임스탬프 생성, `Path`로 디렉터리 생성과 파일 열기를 처리한다.
- **왜?** 외부 의존성이 단 하나도 없다(표준 라이브러리만). append-only JSONL이라는 단순 설계의 직접적 귀결 — DB 드라이버도, ORM도 필요 없다. `logger`를 모듈 레벨에 한 번만 만들어 두는 건 파이썬 로깅의 표준 관용구다.

### 줄별 해설 — `record()` 시그니처

```python
def record(path: str, *, agent: str, tool: str, args: dict, decision: str, trace_id: str) -> None:
    """tool 호출 한 건을 audit JSONL에 한 줄 append한다."""
```

- **의미**: tool 호출 한 건을 받아 audit 파일에 한 줄 추가하는 함수. 반환값은 없다(`-> None`).
- **왜?** `path` 다음의 `*`는 그 뒤 인자들을 **키워드 전용**으로 강제한다. 호출부는 반드시 `record(path, agent=..., tool=..., decision=...)`처럼 이름을 붙여 호출해야 한다. `agent`·`tool`·`decision` 같은 비슷하게 생긴 문자열 인자들이 순서가 뒤바뀌어 들어가는 사고를 컴파일 단계에서 차단한다 — 감사 기록처럼 정확성이 중요한 곳에서 특히 값진 안전장치다.
- **(보충)** `path`를 인자로 받는 이유: audit 파일 경로는 환경변수 `GATEWAY_AUDIT_PATH`로 결정되며(기본 `audit/audit.jsonl`), 그 결정은 호출부가 내려서 넘겨준다. 이 모듈은 "어디에 쓸지"를 모르고 "어떻게 쓸지"만 안다.

### 줄별 해설 — 레코드 한 줄 조립

```python
    line = {
        "ts": datetime.now(timezone.utc).isoformat(),  # UTC ISO8601 — admin 시간 필터의 기준
        "agent": agent,
        "tool": tool,  # prefix 포함 전체 이름(예: ops__query_logs). admin이 prefix로 서버를 도로 추출한다
        "args_summary": json.dumps(args)[
            :256
        ],  # 인자 전체 JSON을 256자에서 절단 — 로그 비대화·민감정보 과다기록 방지
        "decision": decision,
        "trace_id": trace_id,  # OTel trace ID(32 hex) — 게이트웨이 로그·span과 동일 값이라 교차 추적 가능
    }
```

- **의미**: 스펙이 정한 6개 필드를 그대로 가진 파이썬 dict 하나를 만든다.
- **왜 `datetime.now(timezone.utc)`인가?** 로컬 시간이 아니라 **UTC**를 쓴다. 여러 머신·시간대가 섞여도 단일 시계로 정렬·필터가 되어야 admin 페이지의 시간 필터가 신뢰할 수 있다. `.isoformat()`은 `2026-06-15T07:21:03+00:00` 같은 ISO8601 문자열을 만든다 — 사람도 읽고 기계도 파싱하는 표준 포맷.
- **왜 `tool`에 prefix를 그대로 두나?** `ops__query_logs`처럼 `서버__도구` 형태의 prefix 포함 전체 이름을 기록한다. admin 페이지가 이 prefix(`ops__`)를 거꾸로 잘라 "어느 백엔드 서버였나"를 복원하기 때문이다. 정보를 풀어 저장하지 않고 한 문자열에 담아 둔 셈.
- **왜 `args_summary`를 256자에서 자르나?** `json.dumps(args)`로 인자 전체를 문자열로 만든 뒤 `[:256]` 슬라이스로 절단한다. 두 가지 위험을 동시에 막는다 — (1) 거대한 인자가 audit 파일을 비대하게 만드는 것, (2) 인자에 든 민감정보(토큰·전문 등)가 통째로 기록에 남는 것. "요약(summary)"이라는 필드명이 의도를 정확히 드러낸다.
- **왜 `trace_id`인가?** OTel trace ID(32 hex)는 게이트웨이의 일반 로그·OpenTelemetry span과 **같은 값**을 공유한다. 그래서 audit의 한 줄에서 trace_id를 집어 들고 로그·트레이스 시스템으로 건너가 "이 한 번의 호출"의 전체 여정을 교차 추적할 수 있다. 감사 기록이 관측 시스템과 끊기지 않고 이어지는 연결고리다.

### 줄별 해설 — 디렉터리 보장과 append 기록

```python
    try:
        # 부모 디렉터리가 없을 수 있으니 매 기록마다 보장(mkdir -p 동등). 비용 미미.
        Path(path).parent.mkdir(parents=True, exist_ok=True)
        with open(
            path, "a", encoding="utf-8"
        ) as f:  # "a" = append 전용 — 기존 내용을 절대 덮지 않는다
            f.write(
                json.dumps(line) + "\n"
            )  # 줄당 JSON 1개(JSONL) — 부분 기록돼도 나머지 줄은 유효
```

- **의미**: 부모 디렉터리를 만들고(없으면), 파일을 append 모드로 열어, dict를 JSON 문자열로 직렬화해 끝에 `\n`을 붙여 한 줄 쓴다.
- **왜 매번 `mkdir`인가?** `parents=True, exist_ok=True`는 쉘의 `mkdir -p`와 동등하다 — 중간 경로까지 다 만들고, 이미 있으면 조용히 넘어간다. 첫 기록 때 `audit/` 폴더가 아직 없을 수 있어 매 호출마다 보장한다. 이미 존재하면 사실상 비용이 없으니 단순함을 택했다.
- **왜 `"a"` 모드인가?** 이 한 글자가 append-only 철학의 코드적 실체다. `"a"`(append)는 파일 끝에만 쓰고 **기존 내용을 절대 덮지 않는다**. `"w"`(write)였다면 매번 파일을 비우고 새로 썼을 것이다 — 그건 감사 로그로서 치명적 결함. 이 모듈 어디에도 `"w"`나 삭제·수정 경로가 없다는 사실이 "한 번 쓴 줄은 못 고친다"는 보증을 만든다.
- **왜 `json.dumps(line) + "\n"`인가?** 줄마다 완결된 JSON 객체 하나를 쓰고 줄바꿈으로 끝낸다 — 이것이 JSONL(JSON Lines) 포맷이다. 장점: 파일을 통째로 파싱할 필요 없이 한 줄씩 읽으면 되고, 쓰다가 중간에 끊겨 마지막 줄이 깨져도 **그 앞의 모든 줄은 여전히 유효**하다. 부분 손상에 강한 구조다.
- **(보충)** `encoding="utf-8"`로 한글·유니코드 인자도 깨지지 않게 보존한다.

### 줄별 해설 — 기록 실패 처리

```python
    except OSError:
        # 디스크/권한 문제 등 → 호출은 이미 처리됐으니 막지 않고 에러만 남긴다(가용성 우선).
        logger.error("audit write failed (path=%s) — call proceeds", path)
```

- **의미**: 디렉터리 생성이나 파일 쓰기가 `OSError`(디스크 가득 참, 권한 없음 등)로 실패하면, 예외를 다시 던지지 않고 에러 로그만 남긴다.
- **왜 예외를 삼키나?** 이것이 "가용성 > 감사 완결성" 결정의 코드적 실체다. `record()`는 tool 호출이 **이미 처리된 뒤** 사실을 기록하는 단계다. 여기서 예외를 위로 던지면 정상 처리된 호출이 막판에 실패로 뒤집힌다 — 손해가 더 크다. 그래서 예외를 가둬 두고(`logger.error`) 호출은 그대로 성공시킨다.
- **왜 `OSError`만 잡나?** 좁게 잡았다. 파일 I/O의 현실적 실패(디스크·권한)는 `OSError` 계열이다. `args` 직렬화 버그 같은 프로그래밍 오류(`TypeError` 등)는 일부러 잡지 않아 개발 중에 드러나게 둔다 — 진짜 디스크 문제만 가용성 우선으로 무마하고, 코드 결함은 숨기지 않는다는 균형이다.
- **(보충)** 로그 메시지에 `path`를 넣어 "어느 파일 쓰기가 실패했나"를 즉시 알 수 있게 한다.

## 2. Live wiring — audit 기록이 시스템 어디에 연결되는가

`audit.py`는 50줄짜리 작은 모듈이지만, Gateway 거버넌스의 **세 시스템을 잇는 허브**다. (아래 연결 지점은 스펙·design 근거에 따른 설명이며, 호출부 코드 자체는 이 문서의 담당 파일이 아니다.)

1. **라우팅/정책 경로에서 호출됨 (입력 측)** — Gateway가 `tools/call`을 처리하는 경로의 끝에서, 인증·정책·백엔드 호출이 끝나 `decision`이 5종 중 하나로 확정된 순간 `record(...)`가 불린다. `allowed`(정책 통과), `denied`(YAML 정책 거부), `auth_failed`(JWT 인증 실패), `rate_limited`(stretch — 호출 과다로 차단), `error`(UNKNOWN_TOOL·BACKEND_UNAVAILABLE 등 정책 외 실패) — 다섯 경로 전부가 빠짐없이 한 줄을 남긴다. 즉 감사 로그는 "허용된 호출의 로그"가 아니라 **시도된 모든 호출의 로그**다.

2. **S5 메트릭과 어휘를 공유함 (가로 측)** — `decision`의 5종 enum은 `observability.py` 메트릭 라벨과 **정확히 동일**하게 설계됐다(eng review 이슈 2). 두 시스템이 같은 단어로 같은 사실을 기록하기 때문에, 대시보드의 "denied 12건"과 audit의 "denied 12줄"이 결코 어긋나지 않는다. 감사와 관측이 **단일 진실(single source of vocabulary)**을 공유하는 셈이며, `trace_id`가 OTel ID로 공유되는 것도 같은 맥락 — 한 줄에서 메트릭·로그·트레이스로 자유롭게 건너갈 수 있다.

3. **S6 admin 페이지가 직접 읽음 (출력 측)** — admin 페이지는 별도 DB 없이 `audit.jsonl` 파일을 그대로 읽어 화면에 뿌린다. 이때 `tool` 필드의 prefix(`ops__`)로 서버를 복원하고, `ts`로 시간 필터를 걸고, `decision`으로 허용/거부를 색칠한다. 레코드 필드 하나하나가 admin UI의 어떤 컬럼·필터를 위한 것인지 설계 단계에서 이미 정해져 있었다 — 그래서 필드가 6개 그 이상도 이하도 아니다.

이 세 연결을 한 문장으로 묶으면: **`record()`는 정책 경로의 출력(decision)을 받아, 메트릭과 같은 어휘로 직렬화해, admin이 읽을 변조 불가 파일에 영구 append한다.**

## 3. 관통하는 설계 원칙 요약

- **Append-only가 곧 신뢰다.** 수정·삭제 코드 경로가 *존재하지 않는다*는 사실 자체가 "변조 안 됨"의 보증이다. `"a"` 모드 한 글자에 이 철학이 응축돼 있다.
- **가용성 > 감사 완결성 (데모 기준).** 기록 실패는 `OSError`로 잡아 에러 로그만 남기고 호출은 진행시킨다. 감사를 못 남겼다고 정상 요청을 막지 않는다.
- **단일 진실 지점.** `decision` 5종 enum과 `trace_id`를 메트릭·트레이스와 공유해, audit·대시보드·로그가 같은 사실을 같은 어휘로 본다. 숫자가 어긋날 여지를 설계에서 제거했다.
- **최소 구현, 표준 라이브러리만.** DB·인덱스·외부 의존성 없이 JSONL 한 줄 append로 끝낸다. 데모 시스템에 과하지 않은 딱 맞는 크기.
- **부분 손상에 강한 포맷.** 줄당 JSON 1개(JSONL)라, 쓰다 끊겨 마지막 줄이 깨져도 그 앞 줄은 모두 유효하다.
- **민감정보·비대화 방어.** `args_summary`를 256자에서 절단해 거대 인자와 비밀값이 통째로 기록되는 것을 막는다.
- **키워드 전용 인자로 사고 차단.** `record(path, *, agent, tool, decision, ...)`의 `*`가 비슷한 문자열 인자의 순서 뒤바뀜을 호출 단계에서 막는다.
